# Spec — read-deduplicator : Blocked-Reads Log

- **Date** : 2026-06-29
- **Statut** : Draft
- **Dossier de sortie** : `/Users/famillesendrison/neelopedia/stats/read-deduplicator/`
- **Extension touchée** : `~/.pi/agent/extensions/read-deduplicator.ts`

---

## But

Logger chaque `read` bloqué par read-deduplicator dans un fichier markdown
auto-généré, un par session, groupé par cycle d'agent. Le but est qu'un agent
(futur) puisse lire ces fichiers et en extraire des statistiques —
notamment **combien d'octets de reads read-deduplicator a évités** (en
sommant la taille des fichiers bloqués). La conversion en tokens économisés
dépend du modèle utilisé et du contenu des fichiers — ce n'est pas traité ici.

---

## Emplacement des logs

`/Users/famillesendrison/neelopedia/stats/read-deduplicator/<session-id>.md`

- Un fichier par session Pi (pas un seul gros fichier)
- Nommé par l'ID de session Pi (ex : `2026-06-29T17-01-23-a1b2c3d4.md`)
- Si la session est éphémère (pas de fichier `.jsonl`) → `ephemeral-<timestamp>.md`
- Append-only dans chaque fichier
- Le dossier `stats/read-deduplicator/` existe déjà (vault Obsidian neelopedia)
- Pas de rotation, pas d'archivage automatique

### Filtrage des paths sensibles

Pour éviter de logguer des chemins révélant une structure privée, un filtre
optionnel est appliqué côté extension avant l'appel à `addBlock()` :

- Fichier de configuration : `~/neelopedia/stats/read-deduplicator/.pathfilter`
  (une regex par ligne, format `.gitignore`-like)
- Le filtre s'applique sur le chemin **normalisé** (après `path.resolve` et `fs.realpathSync`).
- Si un chemin match une regex → le read est quand même bloqué, mais **pas loggé**
- Si le fichier `.pathfilter` n'existe pas → aucun filtrage (comportement actuel)

Exemple de `.pathfilter` :
```
/Users/famillesendrison/Documents/impôts/
/Users/famillesendrison/Work/client-.*/
```

Le fichier est lu une fois au `session_start`, pas à chaque blocage.

### Origine du Session ID

Le session ID est fourni par Pi via le champ `session.id` du context
d'extension. Format : `<timestamp>_<uuid>` (ex : `2026-06-29T14-29-45-259Z_019f13c9`).

- Détermination faite **une seule fois** sur `session_start` :
  - Si `ctx.sessionManager.getSessionFile()` retourne un path → le
    fichier existe, extraire le nom → `<session-id>.md`
  - Sinon → `ephemeral-<timestamp>.md` (timestamp = `Date.now()`)
- Le résultat est stocké en RAM pour la durée de la session.
- Pas de re-vérification ultérieure (le statut éphémère/persisté ne
  change pas en cours de session).

L'extension ne parse jamais le filesystem pour obtenir l'ID — elle
consomme uniquement ce que Pi lui donne.

### Pourquoi un par session (vs un seul gros fichier)

| Critère | Un gros fichier | Un par session |
|---------|----------------|----------------|
| Lecture par un agent | `read` tout | `ls` + `read` ciblé |
| Taille dans le temps | Grossit indéfiniment | Chaque fichier ≤ quelques MB |
| Suppression / archivage | Tout mélangé | `rm` un fichier = clean |
| Stats isolées | Faut parser `## Session:` | Le nom du fichier = la session |
| Risque corruption | Tout l'historique | Session courante seulement |

## Format du fichier

```markdown
# Read Deduplicator — Blocked Reads Log

> Auto-generated by `read-deduplicator.ts`. Do not edit.
> Format : one line per blocked read, grouped by agent cycle.
> **Format version**: 0.1.0

---

# Session: 2026-06-29T17-01-23-a1b2c3d4

- **Started** : 2026-06-29 17:01:23
- **CWD** : /Users/famillesendrison/Developper/Projects/dotpi

## Cycle 1 — 17:01:23 → 17:03:45 (4 turns)

- **Reads** : 12 tentés / 2 bloqués
- `17:01:45.123` `/Users/foo/bar.ts` (4.2 KB / 4300 B) — turn 2
- `17:02:12.456` `/Users/foo/baz.md` (1.1 KB / 1126 B) — turn 3

## Cycle 2 — 17:05:10 → 17:08:30 (3 turns)

- **Reads** : 7 tentés / 1 bloqué
- `17:05:50.789` `/Users/foo/qux.py` (12.3 KB / 12595 B) — turn 1
```

### Champs par ligne de blocage

| Position | Champ | Exemple | Usage |
|----------|-------|---------|-------|
| 1 | timestamp HH:MM:SS.SSS (Heure locale) | `17:01:45.123` | Quand bloqué |
| 2 | chemin absolu du fichier | `/Users/foo/bar.ts` | Quel fichier |
| 3 | taille human-readable | `4.2 KB` | Lecture rapide |
| 4 | taille en bytes | `4300 B` | Parsing / stats |
| 5 | turn number | `turn 2` | Contexte |

### Contraintes de formatage

- **Pluriel** : accord automatique — `(1 turn)` / `(N turns)`
- **Backticks dans les paths** : les `` ` `` dans les noms de fichiers sont
  échappés (`` \` ``) pour ne pas casser le format markdown.

### Pourquoi human-readable + bytes

- Human-readable : visualisation rapide dans Obsidian
- Bytes : un agent qui parse peut extraire le nombre exact d'octets évités
  → base pour des statistiques cross-session (volume cumulé, tendances…)
- La conversion bytes → tokens dépend du modèle et du contenu, et sort du
  scope de cette spec.

### Format de taille

| Plage | Format | Exemple |
|-------|--------|---------|
| < 1 KB | `<n> B` | `430 B` |
| < 1 MB | `<n.n> KB` | `4.2 KB` |
| < 1 GB | `<n.n> MB` | `12.3 MB` |
| ≥ 1 GB | `<n.n> GB` | `1.5 GB` |

Une décimale max, sauf pour les bytes (entier). La conversion utilise
la base 10 : 1 KB = 1000 B, 1 MB = 1000 KB.

## Cycle d'agent — définition

### Frontières

| Event Pi | Rôle dans le log |
|----------|------------------|
| `agent_start` | Ouvre un cycle. Capture timestamp de début. |
| `turn_start` | Fournit `event.turnIndex` (1-indexé). L'extension maintient ce `currentTurnIndex` en mémoire. |
| `tool_call` (*read*) | Détecte un read bloqué. Transmet path, taille et `currentTurnIndex` à `addBlock()`. |
| `agent_end` | Ferme le cycle. Calcule la durée, flush le buffer. |

**Note** : les noms d'événements ci-dessus sont vérifiés contre
l'API Pi au 2026-06-29 (`~/.pi/agent/docs/extensions.md`, sections
Agent Events / Tool Events). Un *turn* = une réponse LLM + ses tool
calls. Le `turnIndex` est fourni par Pi, pas calculé par l'extension.

### Cas spéciaux à gérer

| Cas | Comportement attendu |
|-----|---------------------|
| Cycle avec 0 blocage | Section `## Cycle` non ajoutée dans le fichier. Numérotation absolue depuis `session_start` (ex: si le cycle 2 est vide, on passe de `Cycle 1` à `Cycle 3`). |
| `agent_end` sans `agent_start` précédent | Impossible (Pi garantit l'ordre `agent_start` → `agent_end`) |
| Pi crash mid-cycle | Buffer en mémoire perdu. Le fichier existant n'est pas corrompu (il manque juste le cycle en cours). |
| Plusieurs cycles dans la même session | Ajoutés séquentiellement dans le même fichier, séparés par une ligne vide |
| Première session dans un fichier inexistant | Header + `# Session:` + premier cycle |
| Nouvelle session dans un fichier existant (peu probable mais possible) | Séparateur `---` + nouveau `# Session:` |

## Mécanisme — buffer par cycle

### Pourquoi buffer (vs write à chaque blocage)

- Crash mid-cycle → fichier avec `## Cycle` non-fermé, moche
- Perte de la métadonnée de durée (calculable seulement à la fin)
- Race conditions théoriques si plusieurs écritures concurrentes

### Avec buffer

- Tout le cycle arrive atomiquement sur disque → fichier toujours propre
- Durée du cycle (`→ HH:MM:SS`) calculable au flush
- Si crash avant `agent_end` → rien n'est écrit, on perd juste le log de ce cycle

### Normalisation des chemins

Avant toute comparaison dans le tracker OU écriture dans le log, le
chemin est normalisé :

1. `path.resolve(cwd, rawPath)` — rend le chemin absolu
2. `fs.realpathSync(normalized)` — résout les symlinks

Le log **écrit le chemin normalisé** (absolu, symlinks résolus), pas le
path brut passé par le LLM. Ceci garantit qu'un même fichier est toujours
représenté de façon identique.

Cas d'erreur : si `realpathSync` échoue (fichier supprimé entre le
`tool_call` et la normalisation), le read n'est pas bloqué et n'est pas
loggé (le fichier n'existe pas, on ne peut pas le lire de toute façon).

### Comportement

- Pendant un cycle : les blocages sont accumulés en RAM
- Flush automatique si le buffer dépasse 2000 entrées (filet de sécurité extrême
  pour éviter la saturation mémoire, ne devrait théoriquement jamais servir vu
  les limites de contexte du LLM).
- Sur `agent_end` :
  - Si buffer vide → rien à faire
  - Si buffer non vide → sérialiser tout le bloc (header de cycle + lignes) → write atomique
- Le buffer est ré-initialisé à chaque `agent_start`

### Garanties

- Aucune intervention LLM : tout est mécanique (syscalls `stat` et `write`)
- Aucune lecture réseau
- Aucune dépendance externe à Pi (le module de log pourrait être testé sans Pi)
- Si le write échoue (disque plein, permissions) → l'extension continue de bloquer les reads normalement, juste sans log
- Si une exception est levée dans `addBlock()` ou `flush()` → catch,
  logguer sur stderr, l'extension continue normalement. Le cycle en cours
  est perdu mais les reads restent bloqués.

### Nouvelle session dans un fichier existant

Si un fichier `<session-id>.md` existe déjà au `session_start` (réutilisation
d'un même ID de session, ex: même CWD + même jour), l'extension :

1. Vérifie si le fichier existe → `fs.existsSync(path)`
2. Si oui → lit les 200 premiers octets pour vérifier que le header
   `# Session:` correspond à la session courante
3. Si le header correspond → le fichier est le bon, on append normalement
4. Si le header est différent (vieux fichier orphelin ou collision d'ID) →
   insère `---` + nouvelle ligne vide + `# Session: <id>`, puis append

Ce cas reste peu probable (les IDs Pi incluent un UUID) mais le mécanisme
garantit qu'un fichier ne mélange pas deux sessions différentes sans
séparateur visible.

### Écriture concurrente et Append-Only

Pour éviter la corruption en cas d'écritures concurrentes (deux instances
Pi, sync Obsidian multi-machine) tout en conservant un fonctionnement
append-only, le flush utilise un processus read-modify-write atomique :

1. Lire le contenu existant du fichier (vide si inexistant).
2. Ajouter le nouveau bloc à la fin de ce contenu en mémoire.
3. Sérialiser l'ensemble dans un fichier temporaire (`<session-id>.md.tmp.<pid>`).
4. `fs.renameSync(temp, final)` — rename est atomique sur POSIX.
5. Si le rename échoue (fichier verrouillé), logguer l'erreur et passer.

*(Note : à l'initialisation lors de `session_start`, l'extension fait un `fs.mkdirSync(dir, { recursive: true })` pour garantir que le dossier parent existe).*

En cas de conflit vrai (deux processus flush en même temps), le dernier
rename gagne — le fichier reste cohérent (un bloc complet, pas un bloc
coupé en deux). La perte éventuelle d'un bloc concurrent est acceptable
(le log est un outil de stats, pas une source de vérité transactionnelle).

Pas de lock fichier : complexité disproportionnée pour ce use case.

### Mode dry-run

Pour tester le logging sans bloquer de vrais reads, une variable
d'environnement `RD_DRY_RUN=true` désactive le blocage effectif :
les reads passent normalement mais sont loggés comme s'ils étaient
bloqués. Utile pour valider le format de sortie et les stats.

### Health-check

L'extension expose un compteur dans le status Pi via
`ctx.ui.setStatus("rd", \`${bloqués} reads bloqués\`)`.
Permet de vérifier en un coup d'œil que le système tourne.

## Architecture (séparation des concerns)

| Module | Responsabilité |
|--------|----------------|
| `extensions/read-deduplicator.ts` | Branche les 4 events Pi ; orchestre tracker + log |
| `agent-hooks/read-deduplicator/src/core/read-tracker.ts` | Map des fichiers déjà lus (existant, inchangé) |
| `agent-hooks/read-deduplicator/src/core/blocked-log.ts` | Buffer en mémoire, formatage, write atomique (nouveau) |

Le module de log :
- Ne connaît pas Pi
- Expose une interface simple (`startSession`, `addBlock`, `endCycle`)
- Peut être testé avec un mock filesystem, sans lancer Pi

L'extension reste l'unique point qui :
- Détecte les events Pi (`agent_start`, `tool_call`, `agent_end`)
- Décide quand un read doit être bloqué
- Appelle `addBlock()` au bon moment
